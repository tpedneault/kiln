### 2.17 REQ-017 The GUI opens any project from a picker and switches between them

**implemented**\
**Implemented by:** [crates/kiln-gui/src/home.rs:205](../../crates/kiln-gui/src/home.rs#L205)\
**Verified by:** [crates/kiln-gui/src/home.rs:1048](../../crates/kiln-gui/src/home.rs#L1048), [crates/kiln-gui/src/home.rs:1137](../../crates/kiln-gui/src/home.rs#L1137), [crates/kiln-gui/src/tests.rs:887](../../crates/kiln-gui/src/tests.rs#L887)

Before K12, `kiln gui` (and `kilnw`) found its project by walking up from the current folder to a `kiln.toml`, and stopped with "no kiln.toml in … or any folder above it" when there was none. So the window couldn't be started from a shortcut, the Start menu or Flint without first being in a project, and looking at a second project meant a second window from a second folder.

The GUI starts anywhere: outside a project it opens on Home, a picker of the projects opened before (most recent first) with a way to add another folder, and inside one `SPC h` goes back to Home to switch to another project without restarting. The list of projects is the user's, not the project's, so it is never in a repository. It lives in Kiln's state folder rather than beside `settings.toml`: its paths are this machine's, and on Windows the settings roam.

From GUI.md, "Home" (K12).

### 2.18 REQ-018 Requirements at several levels trace to each other, and derived ones say so

**implemented**\
**Implemented by:** [crates/kiln-check/src/rules.rs:576](../../crates/kiln-check/src/rules.rs#L576), [crates/kiln-index/src/levels.rs:75](../../crates/kiln-index/src/levels.rs#L75), [crates/kiln-render/src/reports.rs:231](../../crates/kiln-render/src/reports.rs#L231)\
**Verified by:** [crates/kiln-check/src/tests.rs:518](../../crates/kiln-check/src/tests.rs#L518), [crates/kiln-render/src/tests.rs:173](../../crates/kiln-render/src/tests.rs#L173), [crates/kiln/tests/cli.rs:168](../../crates/kiln/tests/cli.rs#L168)

Projects at work write requirements at several levels: what the customer or the stakeholders need, what the system must do, what each piece of software must do; for avionics, DO-178C's high- and low-level requirements. Before K13 Kiln checked one type, `requirement`: a project could declare a type per level and link them, but nothing checked that a system requirement answers a stakeholder requirement, or that every stakeholder requirement was refined, and no report showed the chain from the top level to the code and tests.

Kiln knows the levels and their order. It reports a requirement that answers nothing above it unless it is marked derived, one that nothing below refines, and a link that skips a level. It shows the chains as a traceability matrix, on the command line and in exports, with the derived requirements apart, because that is what an assessor asks for. A project with one level is checked as before.

From FORMAT.md, "Requirement levels" (K13).

### 2.19 REQ-019 Coding agents find how this project's design is organised and how to change it

**implemented**\
**Implemented by:** [crates/kiln-check/src/rules.rs:41](../../crates/kiln-check/src/rules.rs#L41), [crates/kiln-model/src/agents.rs:188](../../crates/kiln-model/src/agents.rs#L188)\
**Verified by:** [crates/kiln-model/src/agents.rs:544](../../crates/kiln-model/src/agents.rs#L544), [crates/kiln/tests/cli.rs:1321](../../crates/kiln/tests/cli.rs#L1321)

Coding agents now implement much of what a design describes, and change the design too. Without guidance they edit front matter by hand, choose IDs, write inverse links and edit generated exports: work `kiln check` then rejects, or worse, accepts and the next export contradicts.

A Kiln project carries a guide that such agents read where they work: how to read and change the design through Kiln's commands, what they may and may not decide, and how this project's design is organised (its types, folders, statuses, links, levels and exports). The organisation part always matches `kiln.toml`, and CI says when it doesn't; the rules are the project's to adapt.

From DESIGN.md, "The agent guide" (K14).

## 3 Decisions

### 3.1 ADR-001 TOML front matter

**accepted**

Items carry TOML between `+++` lines rather than YAML: Kiln edits front matter (status, links) and `toml_edit` keeps the author's comments and layout; TOML is the configuration language of the rest of the suite; and it has no implicit typing surprises.

### 3.2 ADR-002 Sequential IDs, renumbered on collision

**accepted**

IDs are the type's prefix and the next number, readable and said aloud in meetings, over collision-free IDs nobody can remember. Two branches can allocate the same number; `kiln check` finds it and `kiln renumber` fixes it.

### 3.3 ADR-003 One-way publishing to Confluence

**accepted**

Confluence is a published view. Edits made there are detected and reported as drift, never merged back: the repository stays the one source (CONFLUENCE.md).

### 3.4 ADR-004 One design document is the default export

**accepted**

The default export is the whole design as one document on one Confluence page or in one file: one thing to read top to bottom, review and link to, whose page history is the document's revision history. `sections` and `tree` split the same document (EXPORT.md).

### 3.5 ADR-005 Shell out to git

**accepted**

`kiln-git` runs the user's `git` rather than linking a git library, as `fenix-git` does: it already honours their credentials, configuration and repository format, and CI images have it.

### 3.6 ADR-006 One spelling per ID number, at least three digits

**accepted**

FORMAT.md said "no leading zeros" while every example used three digits. Found while writing this folder (K1): IDs are written with at least three digits, zero-padded, and exactly one spelling per number, so `grep` finds an ID as typed and IDs sort as text up to 999. Another spelling is a finding that names the right one.

### 3.7 ADR-007 Links are written once, on their source side

**accepted**

A link is a fact in one place, the item it starts from; its inverse ("verified by") is computed. Writing it on the inverse side is a warning (K109) that says which item to write it in.

### 3.8 ADR-008 Code references are matched on text, not parsed

**accepted**

Source files are scanned with the configured regexes over whole text, not parsed per language. A match inside a string literal counts; in exchange the scanner works for any language and stays within the check budget. Kiln's own tests build such text at run time for that reason.

### 3.9 ADR-009 Exports kept in the repository name no commit

**accepted**

EXPORT.md wanted a committed Markdown export kept current by `kiln export --check`, but also had every export name the exported commit in its summary and link repository files at the last commit that changed them. A file committed into the repository can't name the commit that contains it, so the check could never pass. Found while making this repository's own design document (K2).

A file export inside the repository and not ignored by git is in-tree: it links repository files with relative paths, which GitLab and GitHub resolve at the revision being viewed, and its summary names no commit. Exports outside the repository (Confluence, a file under `target/`) keep naming commits.

### 3.10 ADR-010 kiln stays a console program; kilnw opens the GUI

**accepted**

DESIGN.md planned the Fenix and Flint way for the GUI on Windows: one GUI-subsystem executable that attaches to the terminal it was typed in, with `--console` to force one. Fenix and Flint are GUIs first; Kiln is a command-line and CI tool first, and a GUI-subsystem program isn't waited for by `cmd.exe` and loses its exit code in batch files, which is what CI and scripts rely on. Found when the GUI arrived (K7).

`kiln.exe` stays a console program: `kiln` alone or `kiln gui` opens the window from a terminal. `kilnw.exe`, a GUI-subsystem program next to it, starts `kiln gui` with no console window: what a shortcut or Flint's "Open in Kiln" runs. On Linux and macOS there is one `kiln`; `kilnw` does the same there.

### 3.11 ADR-011 Word files are written directly, not through docx-rs

**accepted**

EXPORT.md planned the `docx` format on the `docx-rs` crate. Building it (K8) showed that `docx-rs` numbers bookmarks, hyperlinks, pictures and headers from process-wide counters, so the same document rendered twice in one `kiln export` comes out with different bytes, and `kiln export --check` (determinism, EXPORT.md) can't hold. It also pulls in an image library Kiln doesn't need, and has no notion of a reference document's styles.

Kiln writes the package itself: WordprocessingML for what the document tree holds (headings, paragraphs, lists, tables, links, bookmarks, pictures, a TOC field), in a zip written by the `zip` crate with its parts in a fixed order and a fixed time. A reference `.docx` is read with the same crate, and its styles, theme, numbering and page setup are copied over, with Kiln's missing styles added. About a thousand lines, every one of them testable as text.

The cost: Kiln owns the subset of the format it writes, and a construct Word users expect that the tree doesn't have (footnotes, headers and footers) needs writing by hand. The tree is small and changes rarely, so that is the cheaper side.

### 3.12 ADR-012 The GUI edits front matter, never prose

**accepted**

K7 made the GUI a reader: it opened items in Fenix and edited nothing, leaving `kiln set`, `link`, `new` and `renumber` to the terminal, the language server and Flint. In use that sent people back to the terminal for every status change, link and new item, and for every export, plan and comment check, which is what the window was meant to save them.

From K9 the GUI edits what `kiln set`, `link`, `unlink`, `new` and `renumber` edit: one-line values (a status, a title, a parent, an owner, a date), links, new items and IDs. It never edits an item's body: prose is written in an editor, and Fenix is that editor. Every value is picked from a list or typed on the footer's single line; there is no text area.

Three things keep the two front doors alike. The checks and the writes are `kiln-index`'s (`plan_set`, `check_link`, `apply_set`, `apply_link`, `apply_renumber`, `create_item`), shared with the command line and the Flint provider, so a value one accepts the others accept and a file an editor saved in the meantime is refused by all three. Exports and comments run the commands' own code through the binary, so the window shows what the terminal prints and never handles a token. Publishing asks first and publishes only the plan it showed; overriding a refused plan (`--force`, `--adopt`) and pruning stay on the command line, where the flag is written down.

### 3.13 ADR-013 Items are a flat list, with one line per relationship

**accepted**

Exports nested items by `parent`: a child was a heading one level below its parent. Read in Confluence, that hid most requirements from the table of contents, which stops at three levels (`toc_levels`): a section is level 1, its items level 2, and every child below that was missing. And an item's properties were one line (`approved · under REQ-002 · verified by TEST-031, TEST-032 · implemented by …`), which is compact but hard to scan once an item has more than two relationships.

Now the items of a `kiln:items` are a flat list of headings at one level, in tree order, each parent followed by its children, so the table of contents lists every item and related items still sit together; the parent shows in the item's properties. `nest="parent"` keeps the old nesting where a document wants it, and `tree` nests by default, because there nesting is what makes the page tree. Properties default to `item_style = "list"`: the status, then one line per relationship with its label in bold, broken inside one paragraph so the block stays short. `line` remains for documents that want the compact form.

### 3.14 ADR-014 Kiln pushes the tasks it manages to Jira

**accepted**

Through K8 Kiln only read Jira: a task changed in Kiln left its ticket behind, and every change was made twice, once in the repository and once in Jira. K207 noticed the difference but couldn't remove it.

From K10, with `[jira] project` set, `kiln jira sync` keeps Jira in step with the items, one way, as publishing keeps Confluence in step ([ADR-003 One-way publishing to Confluence](#33-adr-003-one-way-publishing-to-confluence)). One Jira issue stands for the Kiln project (`[jira] parent`, created by the first sync), and each synced item, the tasks by default, is a sub-task of it. Kiln creates those sub-tasks and keeps their summary, due date and status: the status by the workflow transition that reaches the mapped status (`[jira.status]`, else Jira's status category). A ticket created for an item is recorded in the item (`jira = "…"`), and the project issue in `kiln.toml`, so the commit records the link and no ticket is ever created twice; a person runs the sync, not CI, for that reason.

What stays Jira's: assignees, sprints, comments, worklogs, and every ticket that isn't a sub-task of the project issue, which Kiln never writes even when an item links it. Kiln deletes nothing: a sub-task no item links any more is reported. A ticket moved in Jira is flagged by K207; `kiln jira pull` takes its status back into the item as a reviewable edit, or the next sync moves it back. The repository stays the source of truth ([REQ-001 The repository is the source of truth](#21-req-001-the-repository-is-the-source-of-truth)), and Kiln still holds no assignments or sprints ([RISK-004 The model becomes a second Jira](#5-risks)).

### 3.15 ADR-015 Presets are copied into the project and stack without duplicates

**accepted**

People asked for ready-made documents (arc42 first) that they could add with one command and then adapt, several to one project.

**Copied, not referenced.** `kiln preset add` writes the template into the project's `templates/` folder and its configuration into `kiln.toml`, and from then on all of it is the project's own, changed in its merge requests; a newer Kiln never touches it. A referenced template (`template = "preset:arc42"`) would change under its authors with an upgrade, in the published document of all places, and every team that adapts arc42 to itself (the normal case) would copy it anyway. The cost is that improvements to a preset reach only projects that add it afterwards; `kiln init --preset NAME` in an empty folder writes the current one to compare with.

**Configuration included, the minimum, nothing twice.** A preset adds the types and link roles its template places and an export target, so it works the moment it is added. It adds only what is missing: a type the project already declares, by hand or from another preset, is kept as it is; a role it has gains only the `from` and `to` types it lacks; each preset's export has the preset's name. So `arc42` and `srs` share `constraint` and `term`, in either order. A prefix clash, a taken export name or a file already there stops it before anything is written, and `kiln.toml` is spliced so its comments survive ([REQ-013 Edits keep the author's formatting and never fight an editor](#22-req-013-edits-keep-the-authors-formatting-and-never-fight-an-editor)). The links that go further than the document needs (tests verifying quality scenarios, code implementing building blocks, blocks using blocks) are choices with alternatives, so the wiki's "Presets" page offers them to add by hand rather than the preset making them; a first version that left all configuration to the wiki made every project paste the same tables.

The presets follow the structure of arc42 and ISO/IEC/IEEE 29148 with wording of Kiln's own, since arc42's help text is CC BY-SA and Kiln is MIT OR Apache-2.0.

### 3.16 ADR-016 Requirement levels are types in order, traced upward by a link; derived ones are marked

**accepted**

Requirements written at several levels needed Kiln to know which types are levels, in which order, and how a level answers the one above.

**A type per level, ordered in `[requirements] levels`.** Not a `level` key on each requirement, nor tags: each level has its own prefix (`SYS-004` says what it is in a meeting), its own statuses and its own section in the document, which types already give. Declaring the order once in `kiln.toml` keeps it in one place. Without the table the one level is `requirement`, so no project changes behaviour.

**`parent` within a level, a link across levels.** `parent` already means decomposition and makes the tree and the coverage of children; reusing it across levels would make one requirement's children a mix of finer system requirements and the software requirements that implement it. A link role (`refines` by default, `trace` names another) is written once on the lower side, as every link is ([ADR-007 Links are written once, on their source side](#37-adr-007-links-are-written-once-on-their-source-side)), and can point at several requirements above, which `parent` can't. A requirement with no trace link traces through its parent, so a decomposed subtree links upward once.

**Derived requirements are marked, not inferred.** A lower-level requirement that answers nothing above is either forgotten or deliberate (DO-178C's derived requirements, which go to the safety assessment). `derived = true` in front matter is the one way to say "deliberate"; without it, K208. A key rather than a tag because it changes what the check does, and tags never do.

**Each rule one fact.** K208 (nothing above), K209 (the wrong level above), K210 (nothing below), with K201 and K202 applying to every level their role's `to` names, so a V-model can verify every level and implement only the lowest. A link that skips a level still counts where it points: one wrong link is one finding, not two. The levels report shows the leaf's coverage per chain; each level's own verification is the traceability report with its `type`, rather than a matrix too wide to print.

### 3.17 ADR-017 The agent guide lives in the design folder, its rules written once and its description generated

**accepted**

A Kiln project needed a guide for coding agents ([REQ-019 Coding agents find how this project's design is organised and how to change it](#219-req-019-coding-agents-find-how-this-projects-design-is-organised-and-how-to-change-it)).

**`design/AGENTS.md`, not beside `kiln.toml`.** `kiln.toml` is usually at the repository root, where `AGENTS.md` is the repository's guide to its code: not Kiln's to write, and Kiln never overwrites a file. In the first item folder the guide never collides, sits beside the files it describes, and is read by agents that honour nested `AGENTS.md` files when they work there. The cost: an agent working only on the code may not see it, so the wiki suggests one line in the repository's own guide pointing at it.

**Two parts.** The rules (use Kiln's commands, link from the source side, leave sign-off to people…) are written once and are the project's from then on, like a preset's template ([ADR-015 Presets are copied into the project and stack without duplicates](#315-adr-015-presets-are-copied-into-the-project-and-stack-without-duplicates)): teams differ on what an agent may approve, and a newer Kiln rewriting their words would be a surprise. The description of the project (types, folders, statuses, roles, levels, exports) is generated between two marker lines from `kiln.toml` alone, because a hand-kept copy goes stale the first time someone adds a type, and a stale guide misleads an agent more than none. `kiln agents` rewrites only that section, `kiln preset add` refreshes it, and `kiln check` warns when it no longer matches (K113), as `kiln export --check` does for exports. Generating it from the configuration alone, not the items, keeps it stable across ordinary work and exact to compare.

**Optional.** A project that deletes the section, or the file, has opted out, and K113 says nothing; a warning by default, since a stale guide doesn't break the design.

### 3.18 ADR-018 Ready work is open work whose dependencies are finished; milestones group it, they don't gate it

**accepted**

K15 adds `kiln next`, which lists the work ready to start ([REQ-020 Coding agents read the plan and act on it from the command line](#220-req-020-coding-agents-read-the-plan-and-act-on-it-from-the-command-line)).

**Work** is an item of a type the `part-of` role may link from (`task` by default): what a milestone includes. It is **ready** when it is neither done nor closed, its status isn't `blocked`, and every item it `depends-on` is done or closed. Everything else open is **waiting**, with what it waits on named.

**A milestone groups and orders work, it doesn't gate it.** Work of a milestone that `depends-on` an unfinished one is still ready when its own dependencies are: teams overlap milestones, and a gate would hide the work an agent could pick up. `kiln next` lists the earliest milestone's work first (open milestones in ID order, work in no milestone last), so the order the IDs give is the order an agent sees. The cost: a project that does want a gate writes it, `depends-on` from the first task of the later milestone to the last of the earlier one.

**`blocked` is a status a person sets, so it is honoured** by name, like the other default status names some rules know (`verified`, `superseded`): a project that names it otherwise simply doesn't get that.

The same definitions feed `kiln status` and the plan checks K211–K214, so what `next` calls ready is what `check` and `status` agree on.

### 3.19 ADR-019 An editor the user names for Kiln comes before Fenix; VISUAL and EDITOR come after it

**accepted**

##### Context

`kiln new --open` and the GUI's `Enter` opened items in Fenix, else the operating system's default editor ([REQ-021 A person uses Kiln without an agent: items start with a shape, the first export works, mistakes are said](#221-req-021-a-person-uses-kiln-without-an-agent-items-start-with-a-shape-the-first-export-works-mistakes-are-said)). At work, without Fenix, the default editor for `.md` on Windows is often Notepad or nothing. People already name their editor in `VISUAL` or `EDITOR`, and some want Kiln to use one editor whatever else is installed.

##### Decision

The order is `KILN_EDITOR`, the running Fenix, starting Fenix, `VISUAL`, `EDITOR`, the OS default. `KILN_EDITOR` comes first because the user set it for Kiln on purpose. `VISUAL` and `EDITOR` come after Fenix because they are set for every tool, and a Fenix user's shell often sets them to a terminal editor; putting them first would quietly stop opening Fenix.

A command is split on spaces with quotes, never run through a shell (a path with `&` stays one argument), and `{path}` and `{line}` are replaced, the path appended without `{path}`. From the command line the editor gets the terminal and Kiln waits, as `git commit` does, so `vim` works; the GUI has no terminal to lend and starts it in the background.

##### Consequences

A machine without Fenix opens items where its user expects. A terminal editor in `KILN_EDITOR` doesn't work from the GUI; the docs say to name a windowed one there. Kiln still writes nothing of Fenix's.

### 3.20 ADR-020 A milestone's progress is its own work, everywhere

**accepted**

##### Context

Milestone progress counted the work `part-of` a milestone and of every milestone it `depends-on`, transitively. K15's `kiln status` counted only a milestone's own work, so the GUI's Roadmap, the exported roadmap and `kiln show` disagreed with `kiln status` on the same milestone. The wiki already warned that the transitive count misleads whenever `depends-on` only meant the order: in this repository, [MS-017 K16: a first project that explains itself](#4-milestones) reported K15's tasks as its own.

##### Decision

A milestone's progress is its own work: done out of non-closed, over the work `part-of` it directly or through its parent (a sub-task counts where its task does). One function computes it, and `kiln show`, `kiln status`, the GUI and the roadmap report all use it. `depends-on` between milestones orders them and nothing else, as [ADR-018 Ready work is open work whose dependencies are finished; milestones group it, they don't gate it](#318-adr-018-ready-work-is-open-work-whose-dependencies-are-finished-milestones-group-it-they-dont-gate-it) already says for readiness.

##### Consequences

Every view shows the same numbers. A project that relied on a later milestone counting the earlier one's work sees smaller totals; it can make the later milestone include that work, or read the earlier milestone's own line. The roadmap report's numbers change for such projects, so their committed exports change once.

### 3.21 ADR-021 Test results are matched to code references by the name of the test that follows them

**accepted**

##### Context

`--results` reads a JUnit XML report, the format every test runner can write (cargo-nextest, pytest, JUnit, Jest, go-junit-report), and must tell which code reference each test result belongs to. Code references are matched on text, not parsed ([ADR-008 Code references are matched on text, not parsed](#38-adr-008-code-references-are-matched-on-text-not-parsed)), so Kiln doesn't know where a test function starts.

##### Decision

A `verifies` code reference's test is named by the first declaration after the comment: the name after `fn`, `def`, `func`, `function` or `sub`; else the string in `it("…")`, `test("…")` or `describe("…")`; else the identifier before the first `(`. Attribute and decorator lines (`#[…]`, `@…`) and blank lines are skipped. A JUnit `testcase` matches when its name, or its last `::`, `.` or `/` segment, equals that name; when the report gives a `file`, it must also end with the reference's path. A reference all of whose matches passed counts; one with a failure or error doesn't (K216); one with none, or only skipped ones, didn't run (K217).

##### Consequences

It works across languages and runners without a parser, and an explicit name is never needed for the usual layout (the comment on the line before the test). Two tests of the same name in different files share their results unless the report names files; the safer reading wins (any failure is a failure). Without `--results`, nothing changes: a code reference counts as before.

### 3.22 ADR-022 A code reference covers the code down to the next one

**accepted**

##### Context

`kiln affected` turns a git diff into the requirements it touches. A code reference is a comment on the line before the code it is about, and Kiln doesn't parse code ([ADR-008 Code references are matched on text, not parsed](#38-adr-008-code-references-are-matched-on-text-not-parsed)), so where that code ends isn't known.

##### Decision

A code reference covers its own line down to the line before the next code reference in the same file, or the end of the file. A changed line inside that range touches the reference's targets; a deletion touches the range it was in. An item file that changed touches that item. Each touched requirement is listed with the changed ranges and the references that reached it, and with what verifies it, to re-check.

##### Consequences

It over-reports rather than misses: a reference at the top of a file covers the whole file, which is what a file-level `implements` means. Precision comes from placing references close to their code, which the format already asks for. No language support is needed, and the answer is the same on every machine.
